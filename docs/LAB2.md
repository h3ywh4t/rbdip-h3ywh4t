# ЛР2 — тесты расчёта цены и нормализация БД

`PricingCalculatorTest` фиксирует существующее поведение без изменения формул:
типы клиентов, оба купона, неизвестные и пустые значения, оптовую скидку на
отдельную позицию при количестве больше 10, дополнительную скидку при итоге
больше 1000, порядок применения скидок, ограничение отрицательного итога нулём
и округление HALF_UP только в конце. Отдельно проверяются пустой заказ,
отрицательная цена/количество и существующие исключения при `null`.

Миграция `V2__normalize_customers_and_order_items.sql` переносит контакты в
`customers`. Заказы с одинаковыми именем, адресом и телефоном используют одну
запись клиента; `NULL` и пустая строка различаются. При других контактах создаётся
отдельная запись, поэтому сведения в прежних заказах не перезаписываются.
Уникальное ограничение и `INSERT ... ON CONFLICT` предотвращают дубли контактов
при одновременном создании заказов. `orders.customer_id` и
`order_items.product_id` обязательны и защищены внешними ключами.

В исходной V1 у позиции заказа нет ID товара, есть только название и цена.
Миграция ищет точное совпадение этой пары в `products`. Если совпадения нет,
создаётся товар с историческими названием и ценой; при нескольких совпадениях
выбирается минимальный ID. Восстановить исходный ID однозначно из V1 невозможно.
ID заказов и позиций, количества, статусы, даты и отзывы сохраняются.

Новые позиции ссылаются на выбранный товар без копирования его имени и цены.
В соответствии с заданием эти значения теперь читаются из `products`: при
последующем изменении каталога они изменятся и при чтении заказа. Хранение
исторической продажной цены потребовало бы отдельного требования к модели.

Контракты POST/GET `/orders` сохранены. Связи клиента и товара загружаются вместе
с соответствующими сущностями, чтобы GET работал при `open-in-view: false`.
Отдельный запрос позиций для каждого заказа остаётся задачей ЛР4.

`NormalizationMigrationTest` проверяет миграцию пустой и заполненной БД,
перенос контактов с `NULL`, восстановление исторических товаров, сохранение
данных, внешние ключи и повторный запуск Flyway. `NormalizedOrderTest` проверяет
ссылки на товары, повторное использование клиентов, различие контактов и
отсутствие записей после отклонённого запроса.

Проверка (нужен запущенный Docker; БД тестов изолированы через Testcontainers):

```bash
JAVA_HOME=/Library/Java/JavaVirtualMachines/temurin-21.jdk/Contents/Home mvn -B clean verify
python3 scripts/write_score.py
```

Для ЛР2 должны пройти `lab2_coverage` и `lab2_schema`. Ошибки
`NPlusOneReferenceTest` и `ArchitectureRulesTest` относятся к ЛР4. Maven настроен
на игнорирование ошибок тестов, поэтому нужно смотреть сами отчёты
`target/surefire-reports`, а не только сообщение `BUILD SUCCESS`.

`V1__init.sql`, эталонные тесты, правила CI и расчёт баллов не изменяются.
